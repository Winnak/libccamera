# Pi 4B + standard Camera Module v1.3

This path is implemented for **full-resolution still photographs** with the
standard colour OV5647 and VC4 ISP. The [hardware test results](#hardware-test-results)
cover one Pi 4B configuration. NoIR/IR-modified modules need a different colour
calibration.
Select `--profile ov5647_noir` explicitly for those modules. See the broader
[VC4 profile coverage](TUNING.md) for each profile's validation status.

## Build on the Pi

Use a 64-bit Raspberry Pi OS with the OV5647, Unicam and bcm2835-isp devices
available. Building requires a C17 compiler, CMake and installed Linux UAPI
headers. Runtime needs libc and the kernel interfaces; Python is optional for
analyzing diagnostics. The shading grid uses `/dev/dma_heap/linux,cma` or
`/dev/dma_heap/reserved`; your account needs access to that heap as well as the
media/video/subdevice nodes. Missing heaps or controls produce explicit errors.

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j4
ctest --test-dir build --output-on-failure
./build/ccamera-capture -l
./build/ccamera-capture -c 0 -m
```

Use the index reported for OV5647. Close other camera applications before each
run. For hardware/kernel setup, first check that `rpicam-still` can take a photo
on the same Pi. The library configures its own pipeline and has no libcamera
runtime dependency.

The listing includes the sensor's firmware ID when available. `-I 'ID'` or
`--camera-id 'ID'` selects it using fresh discovery and verifies the opened
sensor, even after `/dev` nodes change numbers. The stderr log records the ID.

## First photograph

```sh
./build/ccamera-still -c 0 -o daylight.ppm --metadata daylight.jsonl \
    --raw daylight.raw --statistics daylight.bsta 2>daylight.log
```

The tool selects the enumerated 2592x1944 10-bit Bayer mode and warms up at that
resolution. The PPM is ordinary binary RGB, with stride padding removed. Raw
and BSTA files contain exactly the saved photograph's producer and statistics
payloads. JSONL records all settling results, configuration and bounded control
write traces. Keep the stderr log too: it identifies the selected driver and
media/video paths. Sensor exposure/gain metadata is **expected**, based on the
configured delay model and acknowledged writes, not an embedded measurement.

The tool requests upright (`Rotate0`) sensor orientation before configuring the
raw path, using the mounting rotation and native horizontal/vertical flips.
The returned Bayer order is passed to the VC4 ISP. Stderr and the JSONL
configuration record report the actual EXIF orientation; JSONL also records
`hflip` and `vflip`. A sensor that cannot provide the requested orientation
returns its supported orientation, so check that result before interpreting the
image. Use an upright marker to confirm physical orientation.

Two startup frames are hidden. A photograph is saved after three trusted results
with converged AE/AWB and effective controls. The default settling deadline is
ten seconds. A timeout fails capture; inspect the metadata, including the
exposure-limit flag (512), instead of assuming a usable photo was saved.

The default exposure policy is the official normal curve (approximately 66.7ms
and 8x at its upper end), using live sensor limits. The example defaults to
`--flicker 50` for 50 Hz mains lighting. Use `--flicker 60` for 60 Hz lighting
and `--flicker off` for steady daylight. Short exposures are not forced up to a whole
lighting cycle. Anti-flicker cannot remove arbitrary LED/PWM illumination flicker.

For a repeatable manually exposed photograph, for example:

```sh
./build/ccamera-still -o manual.ppm --shutter-us 20000 --gain-code 16 \
    --colour-gains 1.5,1.8 --metadata manual.jsonl
```

OV5647 gain code 16 is 1x and 32 is 2x. Manual shutter/gain settings override their
automatic counterparts and wait for the expected effective frame. Specifying
both colour gains disables AWB and chooses the closest calibrated colour
temperature. Manual shutter bypasses anti-flicker quantization. All controls
remain subject to kernel limits. Manual longer exposures may need a longer
`--timeout-ms`.

## Check repeatability on the Pi

Use the same camera ID for all runs. Record `uname -sr`, `uname -m`, `/etc/os-release`,
the board model, module variant and libccamera revision. Run the sustained
check at full resolution, then close and reopen the graph with a different
processed size. The raw sensor mode stays at full resolution.

```sh
./build/ccamera-still -I 'ID' --repeat-check 512 --metadata repeat-full.jsonl \
    2>repeat-full.log
./build/ccamera-still -I 'ID' --repeat-check 64 --size 1280x960 \
    --metadata repeat-small.jsonl 2>repeat-small.log
./build/ccamera-still -I 'ID' --repeat-check 64 --metadata repeat-full-again.jsonl \
    2>repeat-full-again.log
```

Each run holds every common buffer slot with an extra request waiting. It
checks that the first frame stays intact, that dequeue reports held-slot
backpressure, and that stop invalidates held views and leaves the waiting
request drainable as cancelled. It then reuses one request for the specified
number of captures, stopping and restarting every 32. `--timeout-ms` applies
per wait. The initial 1 ms wait records whether it observed a live timeout
before successful completion of the same request. If
`short_wait_timed_out` is false, retain that result as a run without an
observed short timeout.

For the first held result and the first capture in each group of 32, the
check compares sampled raw and RGB payload bytes from the delivered V4L2
mapping with those read through an exported DMA-BUF using
`DMA_BUF_IOCTL_SYNC`. It records the negotiated sizes, request cookies,
raw/RGB timestamps, expected exposure and gain, and sample hashes and byte means.
For the scene change, fix shutter and gain, record when the view changes, and
confirm that the sampled raw and RGB payloads respond. The byte means include
the packed RAW10 bytes. The check tracks open fd counts after each stop and compares
counts before opening and after closing the graph. Record memory use during
the sustained run, and use the separate timing diagnostics
below for physical control-delay evidence. Keep both JSONL and stderr logs,
including any run that fails.

The regression suite injects device failures and verifies recovery and
cleanup. The on-device repeat check exercises normal cancellation, backpressure
and timeout recovery with the camera attached.

## Measure timing before changing defaults

Use a stationary scene with a uniform neutral surface, steady light and ample
headroom before clipping. Daylight is useful for timing measurements. Each run
changes **one** control every 16 sensor frames and holds the other settings fixed.
The diagnostic queues multiple raw Unicam buffers so it can capture consecutive
frames and sample packed Bayer brightness without waiting for ISP jobs. The
default 96 frames include startup and allow at least three clean transitions.

```sh
./build/ccamera-still --diagnostic exposure --timeout-ms 30000 \
    --metadata exposure.jsonl 2>exposure.log
./build/ccamera-still --diagnostic gain --timeout-ms 30000 \
    --metadata gain.jsonl 2>gain.log
./build/ccamera-still --diagnostic vblank --timeout-ms 30000 \
    --metadata vblank.jsonl 2>vblank.log
python3 tools/analyze_sensor_timing.py exposure.jsonl
python3 tools/analyze_sensor_timing.py gain.jsonl
python3 tools/analyze_sensor_timing.py vblank.jsonl
```

The analyzer compares brightness transitions or intervals between raw timestamps
with the SOF write frame. It requires three clean transitions and 80% agreement
and rejects capture failures, gaps and lost traces. The suggested delay is an
**inference** from the captured frames. Inspect plots or raw frames if
illumination or driver timing makes the transition ambiguous. Start with metadata
only. Writing every full-resolution frame with `--raw` can disturb the measurement.

The OV5647 defaults use the measured two-frame exposure/gain and one-frame
VBLANK delays. They retain the driver-dependent flag. To set them explicitly:

```sh
./build/ccamera-still --exposure-delay 2 --gain-delay 2 --vblank-delay 1 \
    -o checked.ppm --metadata checked.jsonl
```

HBLANK stayed fixed in the measurements and retains a provisional two-frame
delay. With the shorter VBLANK delay, the managed scheduler writes a blanking
increase before shutter at the same frame start. A decrease follows the shorter
shutter using the measured delay. Missed SOF events or write deadlines stop
capture and report an error.

## Image comparisons and feedback

Collect a daylight scene, a warm indoor scene, a dark frame and an evenly lit
neutral wall. Check shadow colour, highlight detail, white balance, corner
brightness/colour, noise and sharpening halos. Compare sequentially against
`rpicam-still` with matched shutter/gain and no other application using the camera.
For stronger calibration later, use flat-field and colour-chart captures.

Keep PPM/raw/BSTA files together with JSONL and stderr logs. Record lighting and
whether the photograph matches what you saw. Repeat a successful setting after
stopping/restarting the tool. Review the four comparison scenes before signing
off on image quality.

## Hardware test results

The tests used one Pi 4B with a standard colour Camera Module v1.3 and kernel
`6.18.56-v8+`. The public still API captured at 2592×1944 and 1280×960.
The 512/64/64-frame repeat checks passed for held buffers,
cancellation, live timeout recovery and sampled DMA-BUF reads. During a
native 512-frame run with fixed shutter and gain, both raw and RGB samples
responded to a deliberate obstruction and recovered when the view cleared.

At full resolution, five clean transitions each gave a two-frame exposure and
gain delay. Two five-transition VBLANK runs showed the frame interval changing
one frame after the write. Two 25-request public still runs alternated between
about 20 ms and 125 ms, verifying the applied control metadata and four
frame-length changes per run. Raw timestamp intervals agreed with the planned
timing to within 9.7 µs across both runs.

A daylight test started from about 30 ms and 3× gain. The default capture
settled in 11 results and saved a 2592×1944 RGB/raw/statistics set about 2.7 s
after the first sensor frame. The arrow pointed up in both images. The matched
`rpicam-still` JPEG showed lighter shadows and a weaker cyan tint toward the
edges. The covered-lens pair at about 60 ms and 4× gain had a median Bayer
value of 24 in both captures and a shared purple glow along the top edge.
On an evenly lit neutral surface, the corrected factory shading reduced the
cyan cast, with a green cast still visible near the edges.

Under warm light, AE/AWB settled in eight results at about 2,724 K. The matched
9.978 ms, 3.0625× pair agreed in exposure and rendered the white paper with
slightly different colour. Short RAW10 probes identified a 100 Hz optical
ripple. The 50 Hz setting shortened the automatic shutter from 15.276 ms to
9.978 ms and reduced the fitted raw row-brightness component at 100 Hz from
0.846% to 0.033%. To report results for other boards or modules, use the
[contributor hardware testing guide](../CONTRIBUTING.md#hardware-testing).

## Profile and API details

The original `data/ov5647-vc4.json` comes from the archived libcamera 0.7.2
reference.
Its SHA-256 is `c2688a635f4dc32edf5b091ab77be3f92ae342414a31068e2c2efa0a28440d59`.
Raspberry Pi Ltd's calibration and VC4 mappings retain their BSD attribution.
Regenerate the checked-in C tables with `python3 tools/generate_vc4_profiles.py`.
Neither Python nor the reference archive is needed to build the library.

The profile supplies black level 1024 in the ISP's **16-bit scale**, the sampled
33-point gamma curve, interpolated colour matrix, calibrated R/G/B shading,
green equalisation, DPC, gain-dependent spatial denoise and still-quality colour
denoise/sharpening. Lens shading uses calibration-only correction, without the
scene-adaptive ALSC solver. The Bayesian AWB likelihood/priors use a bounded,
synchronous CT/transverse search instead of upstream's asynchronous quadratic
refinement. Single-channel AE uses centre-weighted regions, the normal exposure
curve and its histogram constraint. Adaptive contrast, HDR, preview switching,
full algorithm parity and individual-module calibration are excluded.

`cc_ipa_vc4_create()` opts into module-specific VC4 tuning, selecting standard
OV5647 by default on this sensor; generic/reference capture is
unchanged. Disable available sensor automatic controls before using it, as the
still example does. `cc_camera_get_sensor_geometry()` and its capture wrapper
supply live crop/flip information; missing geometry is an error for this profile.
`cc_capture_configure_sensor_policy()` enables startup filtering, and trace APIs
provide bounded in-memory records. Typed request tuning is copied and overrides
the module's full VC4 block; explicit native ISP controls override matching
profile controls at submission. Native controls omitted by the caller retain
existing semantics. The backend owns the shading DMA buffer through ISP close,
including failure paths, and synchronizes CPU writes before hardware use.

**IPA ABI is now 8.** Recompile C IPA modules and consumers against the new
headers. JPEG encoding remains the caller's responsibility.
