# Pi 4B + standard Camera Module v1.3

This path is implemented for **full-resolution still photographs** with the
standard colour OV5647 and VC4 ISP. Physical capture, control latency and image
quality still need validation on your Pi. NoIR/IR-modified modules need a different
colour calibration. There is no automatic module-type detection.

## Build on the Pi

Use a 64-bit Raspberry Pi OS with the OV5647, Unicam and bcm2835-isp devices
available. Building requires a C17 compiler, CMake and installed Linux UAPI
headers. Runtime needs libc and the kernel interfaces; Python is optional for
analyzing diagnostics. The shading grid uses `/dev/dma_heap/linux,cma` or
`/dev/dma_heap/reserved`; your account needs access to that heap as well as the
media/video/subdevice nodes. Missing heaps or controls produce explicit errors.

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j4
ctest --test-dir build --output-on-failure
./build/ccamera-capture -l
./build/ccamera-capture -c 0 -m
```

Use the index reported for OV5647. Close other camera applications before each
run. For hardware/kernel setup, first check that `rpicam-still` can take a photo
on the same Pi. The library configures its own pipeline and has no libcamera
runtime dependency.

The listing includes the sensor's firmware ID when available. `-I 'ID'` or
`--camera-id 'ID'` selects it using fresh discovery and verifies the opened
sensor, even after `/dev` nodes change numbers. The stderr log records the ID.

## First photograph

```sh
./build/ccamera-still -c 0 -o daylight.ppm --metadata daylight.jsonl \
    --raw daylight.raw --statistics daylight.bsta 2>daylight.log
```

The tool selects the enumerated 2592x1944 10-bit Bayer mode and warms up at that
resolution. The PPM is ordinary binary RGB, with stride padding removed. Raw
and BSTA files contain exactly the saved photograph's producer and statistics
payloads. JSONL records all settling results, configuration and bounded control
write traces. Keep the stderr log too: it identifies the selected driver and
media/video paths. Sensor exposure/gain metadata is **expected**, based on the
configured delay model and acknowledged writes, not an embedded measurement.

The tool requests upright (`Rotate0`) sensor orientation before configuring the
raw path, using the mounting rotation and native horizontal/vertical flips.
The returned Bayer order is passed to the VC4 ISP. Stderr and the JSONL
configuration record report the actual EXIF orientation; JSONL also records
`hflip` and `vflip`. A sensor that cannot provide the requested orientation
returns its supported orientation, so check that result before interpreting the
image. Physical orientation still needs validation on the target board.

Two startup frames are hidden. A photograph is saved after three trusted results
with converged AE/AWB and effective controls. The default settling deadline is
ten seconds. A timeout fails capture; inspect the metadata, including the
exposure-limit flag (512), instead of assuming a usable photo was saved.

The default exposure policy is the official normal curve (approximately 66.7ms
and 8x at its upper end), using live sensor limits. `--flicker 50` is the indoor
default for Denmark/Europe. Use `--flicker off` for daylight or non-mains lighting,
or `--flicker 60` where appropriate. Short exposures are not forced up to a whole
lighting cycle. Anti-flicker cannot remove arbitrary LED/PWM illumination flicker.

For a repeatable manually exposed photograph, for example:

```sh
./build/ccamera-still -o manual.ppm --shutter-us 20000 --gain-code 16 \
    --colour-gains 1.5,1.8 --metadata manual.jsonl
```

OV5647 gain code 16 is 1x and 32 is 2x. Manual shutter/gain settings override their
automatic counterparts and wait for the expected effective frame. Specifying
both colour gains disables AWB and chooses the closest calibrated colour
temperature. Manual shutter bypasses anti-flicker quantization. All controls
remain subject to kernel limits. Manual longer exposures may need a longer
`--timeout-ms`.

## Measure timing before changing defaults

Use a stationary scene with a uniform neutral surface, steady light and ample
headroom before clipping. Daylight is useful for timing measurements. Each run
changes **one** control every 16 sensor frames; all other settings are fixed.
There is no AE/AWB feedback during these runs. The default 96 delivered frames
allow at least three transitions. The first startup frames are retained for
inspection.

```sh
./build/ccamera-still --diagnostic exposure --timeout-ms 30000 \
    --metadata exposure.jsonl 2>exposure.log
./build/ccamera-still --diagnostic gain --timeout-ms 30000 \
    --metadata gain.jsonl 2>gain.log
./build/ccamera-still --diagnostic vblank --timeout-ms 30000 \
    --metadata vblank.jsonl 2>vblank.log
python3 tools/analyze_sensor_timing.py exposure.jsonl
python3 tools/analyze_sensor_timing.py gain.jsonl
python3 tools/analyze_sensor_timing.py vblank.jsonl
```

The analyzer compares brightness transitions or SOE frame periods with the SOF
write frame. It requires three clean transitions and 80% agreement. Failed runs,
sequence gaps and lost trace records are rejected. Its suggested delay is an
**inference**, not proof of register-latch timing. Inspect plots/raw frames if
illumination or driver timing makes the transition ambiguous. Raw capture can
be enabled with `--raw`; writing every full-resolution raw frame is substantial
I/O and can disturb the measurement, so start with metadata only.

The provisional exposure/gain/VBLANK/HBLANK delays are all two frames and remain
marked driver-dependent. To test measured overrides:

```sh
./build/ccamera-still --exposure-delay 2 --gain-delay 2 --vblank-delay 2 \
    -o checked.ppm --metadata checked.jsonl
```

No override is persisted automatically. HBLANK stays fixed during automatic
capture; its configured delay matters only for explicit HBLANK plans. VBLANK
must have at least the exposure delay for the automatic planner to be enabled.
Missed SOF events or write deadlines stop the graph rather than publish a false
association between settings and an image.

## Image comparisons and feedback

Collect a daylight scene, a warm indoor scene, a dark frame and an evenly lit
neutral wall. Check shadow colour, highlight detail, white balance, corner
brightness/colour, noise and sharpening halos. Compare sequentially against
`rpicam-still` with matched shutter/gain and no other application using the camera.
For stronger calibration later, use flat-field and colour-chart captures.

Keep PPM/raw/BSTA files together with JSONL and stderr logs. Record lighting and
whether the photograph matches what you saw. Repeat a successful setting after
stopping/restarting the tool. Hardware checks remain pending until these results
are reviewed; passing host tests does not validate physical pixels or latency.

## Profile and API details

The original `data/ov5647-vc4.json` comes from the archived libcamera 0.7.2
reference.
Its SHA-256 is `c2688a635f4dc32edf5b091ab77be3f92ae342414a31068e2c2efa0a28440d59`.
Raspberry Pi Ltd's calibration and VC4 mappings retain their BSD attribution.
Regenerate the checked-in C tables with `python3 tools/generate_ov5647.py`.
Neither Python nor the reference archive is needed to build the library.

The profile supplies black level 1024 in the ISP's **16-bit scale**, the sampled
33-point gamma curve, interpolated colour matrix, calibrated R/G/B shading,
green equalisation, DPC, gain-dependent spatial denoise and still-quality colour
denoise/sharpening. Lens shading uses calibration-only correction, without the
scene-adaptive ALSC solver. The Bayesian AWB likelihood/priors use a bounded,
synchronous CT/transverse search instead of upstream's asynchronous quadratic
refinement. Single-channel AE uses centre-weighted regions, the normal exposure
curve and its histogram constraint. Adaptive contrast, HDR, preview switching,
full algorithm parity and individual-module calibration are excluded.

`cc_ipa_vc4_create()` opts into OV5647/VC4 tuning; generic/reference capture is
unchanged. Disable available sensor automatic controls before using it, as the
still example does. `cc_camera_get_sensor_geometry()` and its capture wrapper
supply live crop/flip information; missing geometry is an error for this profile.
`cc_capture_configure_sensor_policy()` enables startup filtering, and trace APIs
provide bounded in-memory records. Typed request tuning is copied and overrides
the module's full VC4 block; explicit native ISP controls override matching
profile controls at submission. Native controls omitted by the caller retain
existing semantics. The backend owns the shading DMA buffer through ISP close,
including failure paths, and synchronizes CPU writes before hardware use.

**IPA ABI is now 5.** Recompile C IPA modules and consumers against the new
headers. JPEG encoding remains the caller's responsibility.
